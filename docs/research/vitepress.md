## 1. Big picture

VitePress is ~4 layers: (a) a set of **Vite plugins** (`src/node/plugin.ts`) that turn `.md` into Vue SFCs and virtual modules, (b) a **markdown-it pipeline** (`src/node/markdown/`) that is otherwise framework-agnostic, (c) a **client runtime** (`src/client/app/`) — a hand-rolled router + data injection, no vue-router, and (d) a **default theme** (`src/client/theme-default/`) that is just a Vue component library conforming to a small `Theme` interface. Build = one client bundle + one SSR bundle, then render every known page to static HTML. Dev = plain `createViteServer` (`src/node/server.ts`) with those plugins; no separate dev pipeline.

## 2. Markdown → routes/pages

- **Page discovery**: `resolvePages()` in `src/node/plugins/dynamicRoutesPlugin.ts` — glob `**/*.md` under srcDir, split static pages vs dynamic routes (`[param].md`), resolve rewrites. No crawling: the page list is fully known from the filesystem + route loaders before build.
- **md → Vue**: `createMarkdownToVueRenderFn` in `src/node/markdownToVue.ts`. Renders md via markdown-it (`src/node/markdown/markdown.ts`), collects from the render `env`: frontmatter (gray-matter via `@mdit-vue/plugin-frontmatter`), headers/toc, extracted `<script>`/`<style>` SFC blocks (`@mdit-vue/plugin-sfc`), links for dead-link checking, includes (files pulled in by `<!-- @include: -->`). Then assembles a Vue SFC string: user scripts + injected `<script>` exporting `__pageData` (JSON.parse'd, `<` escaped) + `<template><div>{html}</div></template>` + styles. LRU cache keyed by (src hash, resolution timestamp, relative path).
- **Plugin chain** (`src/node/plugin.ts` `createVitePressPlugin`): the vitepress plugin's `transform` returns the SFC source for `.md` ids; `@vitejs/plugin-vue` (included with `include: /\.(vue|md)$/`) then compiles it. Plugin order: vitepress, rewrites, plugin-vue, hmr-fix, webFonts, user plugins, assetsBase, icons, localSearch, staticData, dynamicRoutes.
- **Entry naming**: every page is a **build entry** (`src/node/build/bundle.ts`): `foo/bar.md` → input name `foo_bar.md` → chunk `assets/foo_bar.md.[hash].js`. The client maps URL → chunk name via `pathToFile()` in `src/client/app/utils.ts` + a `__VP_HASH_MAP__` (page→hash) injected into each HTML; a `hashmap.json` is also emitted so a long-lived tab can recover after a redeploy (`src/client/app/router.ts` retry logic).
- **Dynamic routes**: `foo/[id].md` + sibling `foo/[id].paths.ts` exporting `defineRoutes({ paths, watch, transformPageData })`; the plugin's `load` hook serves the template file's content with a `__VP_PARAMS_START{...}__VP_PARAMS_END` params prefix and optional `<!-- @content -->` CMS-injected raw markdown. Params end up in `__pageData.params`.

## 3. Theme system

- **Contract** (`src/client/app/theme.ts`): `Theme = { Layout?, enhanceApp?(ctx), setup?, extends?, NotFound? }` — 5 fields total. Everything else is convention.
- **Resolution** (`src/node/config.ts` line ~164): if `<root>/.vitepress/theme/` exists it becomes `themeDir`, else the default theme ships in-package. The client imports it via the `@theme/index` alias (`src/node/alias.ts`), so `vitepress/theme` (default) and a user theme are the same mechanism. Package exports: `vitepress` → client runtime, `vitepress/theme` → default theme.
- **Extension** (`resolveThemeExtends` in `src/client/app/index.ts`): recursive shallow merge; `enhanceApp`/`setup` chain base-first. A user theme is typically `{ extends: DefaultTheme, Layout: ... }` wrapping the default `Layout.vue` and forwarding ~35 named slots (nav/sidebar/doc/home-hero/aside — see `Layout.vue`) — this is the whole "slot" story: plain Vue slots, no formal slot registry.
- **Layout selection** is frontmatter-driven: `VPContent.vue` switches `frontmatter.layout` ∈ `home|page|doc|false` (or a registered custom component name). **Nav/sidebar** are not plugins: `themeConfig.nav`/`themeConfig.sidebar` (multi-sidebar keyed by path prefix, resolved per-route in `src/client/theme-default/support/sidebar.ts`) are plain config consumed by the theme; frontmatter (`sidebar: false` etc.) overrides per page. Auto sidebars from content are done by users via `createContentLoader` in a `sidebar.data.ts`, not built in.

## 4. SSG, dead links, fallback, hydration

- **Build** (`src/node/build/build.ts` → `bundle.ts` → `render.ts`): (1) client build (all pages as entries; manual chunk grouping `theme`/`framework`/`assets` via `staticImportedByEntry` graph walk so theme edits don't rehash every page); (2) SSR build to a temp dir (entry `app/ssr.js` exporting `render(path)` = createApp + router.go + `renderToString`, `src/client/app/ssr.ts`); (3) `render.ts` imports that entry with a fresh module registry per run, calls `render(routePath)` per page, and **writes the HTML shell itself** (string template): title/description from pageData, modulepreloads (app chunk imports + page chunk imports + the page's `.lean.js`), CSS, `transformHead`/`transformHtml`/`postRender` hooks, then `pMap` concurrency 64.
- **Lean chunks / hydration optimization**: `renderChunk` in `plugin.ts` regex-marks `createStaticVNode(...)` strings; `generateBundle` emits a duplicate `.lean.js` per page with static strings stripped (`""`). The initial load fetches only the lean chunk — the static HTML is already in the document; full chunk loads later if needed. *(Marko note: Marko 6 resumability makes this entire trick unnecessary — no hydration cost for static content to begin with.)*
- **Dead links**: checked at **compile time** in `markdownToVue.ts`, not by crawling: every internal link collected during render is resolved against the known page list (+ rewrites + `public/*.html`), with `ignoreDeadLinks` config (bool/`localhostLinks`/string|RegExp|fn patterns). Failures abort the build in `renderStart`.
- **SPA fallback**: no server. Unknown routes in the client router catch the dynamic-import failure, re-fetch `hashmap.json` once (redeploy recovery), then fall back to the theme's `NotFound`/`isNotFound` page data. Hosts serve `404.html`. `mpa: true` mode drops the app bundle entirely (no JS unless a page has `<script client>`, which `buildMPAClient.ts` extracts during the SSR transform and bundles separately).
- **Client router** (`src/client/app/router.ts`): ~350 lines, history API + capture-phase click interception on `a[href]` (`getRoutableLinkUrl` filters target/download/`.vp-raw`/cross-origin), popstate with scroll restoration, hashchange, route hooks (`onBeforeRouteChange` etc.). Route = `{ path, component, data }`; component = the page's md chunk; `data` = its `__pageData`.

## 5. Data loading, search

- **`*.data.ts`** (`src/node/plugins/staticDataPlugin.ts`): convention `.data.(m|c)?(j|t)s`. A `load` hook intercepts the id, loads the file **out-of-band via Vite's `loadConfigFromFile`** (so loaders are Node code: TS/ESM, can hit DBs/APIs, may import npm deps), runs `load(watchedFiles)`, and returns `export const data = JSON.parse(...)` — the loader code itself never ships to the client. HMR: module graph of loader deps + `watch` globs (picomatch) drive invalidation; build dedupes the double client/SSR load with a shared promise. `createContentLoader` (`src/node/contentLoader.ts`) is a helper producing such a loader: globs md, gray-matter frontmatter, mtime-cached optional render/excerpt, `transform()`, and URL computation identical to the page pipeline (rewrites, cleanUrls).
- **Local search** (`src/node/plugins/localSearchPlugin.ts`): virtual module `@localSearchIndex` → per-locale `() => import('@localSearchIndex/<locale>')` lazy chunks. Indexing = re-render every page through the *same* markdown renderer, split HTML into heading sections by regex, feed MiniSearch (`fields: [title, titles, text]`). In dev it indexes eagerly and HMR-updates the virtual module; in prod the index builds on first import. Algolia is the alternative provider (client-only, tree-shaken via `__ALGOLIA__` define).

## 6. Markdown extensions

All in `src/node/markdown/`: containers (`::: tip`, `::: details`, code-group, custom containers, GFM alerts `> [!NOTE]` — `plugins/containers.ts`), shiki highlighting (`plugins/highlight.ts`: dual light/dark themes via `themes`+`defaultColor:false`, notation diff/focus/highlight transformers, lazily-loaded languages, `v-pre` on non-`-vue` blocks so Vue mustaches in code don't execute), `preWrapper` (language label + copy button), lineNumbers, snippet `<<< @/file` region includes, `<!-- @include: -->` md inclusion, link normalization (.html suffix, external target=_blank), image plugin, anchor permalinks, attrs/emoji/tasklist/footnote/CJK-emphasis. **Custom components in md** need zero machinery: the output *is* a Vue template, so any imported/registered component tag just works (imports live in the md's own `<script setup>`); `@mdit-vue/plugin-component` only makes the tag rendering whitespace-stable. `eagerFrontmatterInterpolation` inlines `{{ $frontmatter.x }}` at md-render time so anchors/search/content-loader see resolved text.

## 7. What a WordPress-like product adds (general knowledge)

A WordPress-like product differs from a docs SSG in where content and trust live. WordPress is a **server-rendered dynamic application**: content lives in a database (posts/pages/CPTs as rows, not files), and every request is resolved by querying the DB, running the content through a plugin filter chain (`the_content` etc.), and rendering a theme template — with an **admin UI** (editor, media library, revision history) as a first-class part of the product, plus **auth/users/roles/capabilities** gating both the admin and front-end visibility. That implies sessions, CSRF protection, an executable plugin ecosystem with hook points (actions/filters), and often multi-tenancy. The trade-off versus an SSG is that pages aren't prebuilt: every view pays query + render cost, and scaling means caching layers (page cache, object cache, CDN).

The industry has converged on two architectures for combining rich editing with modern front-ends. **Headless CMS + SSG/SSR**: the CMS (WordPress headless, Contentful, Sanity, Strapi) becomes a content API with the admin UI, and the site is built from it — statically at build time (with webhook-triggered rebuilds/ISR when content changes) or server-rendered per request. This is exactly the seam VitePress's dynamic routes already hint at (`paths.ts` loaders returning `{ params, content }` with `<!-- @content -->` injection is documented as "intended for integration with CMS"). **Server-rendered dynamic**: an app server (Laravel, Rails, or a Node meta-framework) queries the DB per request and streams HTML — necessary when content is personalized, access-controlled, or high-velocity.

For a Marko-based product this suggests a staged design: ship the docs/content SSG first (files in, static HTML out — Marko 6's streaming SSR and resumability map directly onto VitePress's SSR-bundle + render-per-page loop, minus the lean-chunk hack), keep the page-data/dynamic-route seams CMS-ready (loaders already can fetch from an API), and add the WP layers later behind them: a DB content model, an admin editor writing to it, auth/session middleware, and rebuild-or-ISR on publish. The plugin ecosystem is the piece with no VitePress analogue — it would need deliberate hook points (markdown transform, page-data transform, layout slots, route resolution) rather than WP-style global action/filter dispatch.

## 8. Vue-specific vs portable

**Vue-specific (needs a Marko equivalent decided):**
- `@vitejs/plugin-vue` compiling the generated SFC; the md→framework-component boundary (`markdownToVue.ts` `vueSrc` assembly, `injectPageDataCode`). Marko equivalent: emit a virtual `.marko` module (raw HTML body via `$!{html}` interpolation) compiled by `@marko/vite`; `__pageData` ports unchanged as a virtual-module JSON export.
- `createSSRApp` + `renderToString` per page (`ssr.ts`) → Marko's streaming `render` + resume; `createStaticVNode` lean-chunk stripping (`plugin.ts` renderChunk/generateBundle) → **delete entirely**, resumability makes it moot.
- Theme `Layout` slots (35 forwarded slots in `Layout.vue`), `enhanceApp`/provide/inject → Marko has no slots-based extension convention; needs a designed equivalent (e.g. layout receives named render-body sections, or `<Layout>` composed of overridable components resolved via the theme's exports).
- `v-pre` interplay (mustaches in code blocks), `@mdit-vue/plugin-sfc`/`plugin-component` — replaceable; `{{ }}` protection becomes moot if md output is inert HTML, not a live template.
- vue-specific `renderChunk`/docsearch CSS regex fixups.

**Portable to any Vite framework (near copy-paste in design):**
- The plugin-suite shape: transform `.md` → page module, virtual modules (`@siteData`, `@localSearchIndex`), alias-based theme resolution, dev-server HTML shell middleware (`configureServer` in `plugin.ts`).
- Page-as-entry multi-build + `pageToHashMap` + `hashmap.json` redeploy recovery (`bundle.ts`, `utils.ts pathToFile`, `router.ts`).
- The whole markdown-it layer and plugin set (`src/node/markdown/**`), dead-link compile-time checking, `ignoreDeadLinks`, rewrites, cleanUrls.
- `*.data.ts` out-of-band loader execution via `loadConfigFromFile` + watch-glob HMR (`staticDataPlugin.ts`); `createContentLoader`; dynamic routes with `paths.ts` + params/content injection; local search (MiniSearch + per-locale lazy chunks); frontmatter→PageData/headers/toc extraction; `transformHead`/`transformHtml`/`transformPageData`/`postRender` hook set; sitemap; MPA mode concept.

**Key numbers**: default theme = 1 Layout + ~60 components; Theme contract = 5 fields; client router ≈ 350 lines hand-rolled; ~15 markdown-it plugins; build = 2 Vite builds + per-page render at concurrency 64.
