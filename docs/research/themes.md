## 2. 主题是什么：四种形态

- **VitePress：接口**。主题 = 一个导出 `{ Layout, enhanceApp, NotFound, Layout: home }` 的模块。默认主题不是特殊存在，任何包实现该接口即可替换。插槽最多（34 个命名 slot），但插槽本身只解决「塞内容」，不改结构。
- **Starlight：集成**。主题层同时接管路由、i18n、SEO、head——定制它就是定制整个站。27 个组件 override 走虚拟模块，无需拷贝源码。代价：主题与 Astro 耦合深，`theme-as-heavy-integration`。
- **Nextra：分层包**。框架层（编译管线 + page map + 无样式基础组件）/主题层（视觉）peer 耦合，blog/docs 两主题共享同一编译产物——「结构组件在框架层、视觉在主题层」是它能多主题的关键。
- **Docusaurus：别名链**。content 插件只产出 `component: '@theme/DocItem'` **字符串**，三层 webpack 别名（`@theme` 用户覆盖 → `@theme-original` 主题原件 → `@theme-init` 初始实现）解析。这是四家里最优雅的解耦：数据面只认槽位名，实现面随意替换，Rspack/Vite 的 resolve.alias 即可实现等价物。

**共同点**：四家都是「主题 = 组件包 + 可发现清单（接口/虚拟模块/别名/tags-dir）」，没有一家把布局焊死在框架里。

## 3. 侧边栏：从手配到全自动的光谱

```
VitePress ──── Starlight ────────── Docusaurus ──── Nextra
纯手配         配置驱动+可选自动      autogen+手配混排    全自动+目录级覆盖
（与文件树可漂移）                    （生成器可替换）    （文件树即唯一事实源）
```

### 3.1 排序规则对照（自动生成侧）

| 规则 | Starlight | Nextra | Docusaurus |
|---|---|---|---|
| 显式序 | frontmatter `sidebar.order ?? MAX` | `_meta` 文件内 key 出现顺序 | frontmatter `sidebar_position` |
| 命名约定 | —（纯字母序兜底） | index 自动置顶 | 文件名数字前缀（`^(\d+)[-_.]`，日期样忽略，剥前缀得 id/label） |
| 分类入口 | 目录即分组 | `index.md` | 约定式：文件名 ∈ {index, readme, 父目录名}，其 label/position 提升为分类元数据 |
| 兜底序 | `Intl.Collator` | 字母序垫底（在所有 meta 项之后） | 字典序（lodash sortBy position→source） |
| 目录元数据 | frontmatter（sidebar.label 等） | 目录级 `_meta.{json,js,ts}` | `_category_.{json,yml,yaml}` |
| 错配处理 | 配置引用不存在页 → 报错 | `_meta` 悬空引用 → **构建期 throw** | Joi 校验 + 生成器可替换 |

- **VitePress 的痛点**（光谱最左）：sidebar 纯手配，改文件名不同步、新文件不出现——配置与文件树漂移。
- **Nextra 的赌注**（光谱最右）：文件系统即唯一事实源，`_meta` 只做有序覆盖 + fail fast。代价是想刻意隐藏/重排必须借隐蔽的元数据规则（`display: hidden/children`、`type: separator/page/menu`）。
- **Docusaurus 的优先级链**是四家里最完整的：显式 frontmatter > 目录元数据 > 命名约定（数字前缀/约定式 index）> 字典序兜底，且分类入口文档的元数据**提升**为分类属性。

### 3.2 光谱结论

排序链的「共识骨架」：**显式 frontmatter > 目录级元数据 > 命名约定 > 字典序**，分歧只在每层做多重。index 置顶/约定式分类入口是低成本的强约定（三家都有等价物）。

## 4. 定制机制：五个层次（按侵入度）

1. **CSS 变量**（四家都有）：改 token 不碰组件。`--vp-*`/`--sl-*`/`--ifm-*`/`--nextra-primary-*`。
2. **配置面**：themeConfig（navbar/footer/TOC 开关…）。Nextra 用 zod safeParse + `.meta()` 生成 API 文档——配置、校验、文档三合一。
3. **插槽**（VitePress 34 命名 slot / Nextra ReactNode props）：往布局塞内容，不改结构。
4. **组件替换**（Starlight 27 组件 override 虚拟模块 / Docusaurus wrap）：换实现但保留升级通道（`@theme-original` 可无限嵌套 wrapper）。
5. **源码分叉**（Docusaurus eject）：CLI 拷贝主题源码进用户目录，从此该组件归用户——**官方自己都用 unsafe 标签 + 危险确认劝退**。v2→v3 大迁移曾强制全量重 swizzle，社区教程「第一步 eject Layout」是官方承认的生态病。

**教训**：高频定制（配色、小 UI 件）要挡在第 1–3 层；第 4 层要保「组合优先」（wrap 一等公民、可找回原件）；第 5 层的长期代价全部落在用户身上。Docusaurus 事后补的「注册表组件」（`NavbarItem/ComponentTypes` eject 来注册新类型、`Admonition/Types` 加 admonition 类型）正是这个教训的产物：**加类型 > 换组件**。

另：Docusaurus 给每个可覆写槽位配 57KB 类型契约（`theme-classic.d.ts` 逐组件 declare module）+ 55 条 `{wrap, eject} ∈ {safe, unsafe, forbidden}` 稳定性分级表——契约要标注「公共 API / 内部 API」，且未声明者默认档要有立场。它的 forbidden 大量存在只因「CLI 处理目录会崩」（源码注释自认）——**别把实现债编码进公共契约**。

## 5. 暗色切换（共识度最高的部分）

四家工程上是同一套，差异只在细节：

1. **pre-paint 内联脚本**（`<head>` 或 body 前，SSR HTML 一到就执行）：读 localStorage → 解析系统偏好 → 设置 html 属性/class。SSG 静态 HTML 对所有用户相同，**这一步无法省略**（不存在按请求写死主题的时机）。
2. **DOM 标记**：VitePress/Nextra 用 class，Starlight/Docusaurus 用 `data-theme` 属性。属性派更优：不占 class 命名空间、可携带语义（Docusaurus 另设 `data-theme-choice="light|dark|system"`，system 用显式值方便用户 CSS）。
3. **存储键**：各自 namespace（`vitepress-theme-appearance` / `starlight-theme` / `theme`）。Nextra/Starlight 把「跟随系统」存为空串/删键；Docusaurus 删键 + `?docusaurus-theme=dark` 查询参数一次性强制 + 3.8 起 storage 可 namespace 化（多站同 origin 互踩键的教训，GitHub Pages 项目站场景）。
4. **切换 UI**：循环按钮（VitePress）vs 三态下拉（Nextra）vs 两态按钮 + system 只存在于 API（Docusaurus）。
5. **水合一致性**：React 系都要刻意延迟初始化防 hydration mismatch（Docusaurus issue #7986、Nextra `useMounted()` 固定渲染 light）。对 Marko resume 的启示：**主题状态不进组件状态**，纯 DOM attribute + 手写脚本，连 resumable 状态都不用建。
6. **反闪杂项**：Nextra Banner 关闭态用水合前内联脚本读 localStorage 切类；Docusaurus `meta theme-color` 双 media 标签；Starlight 同。这些模式直接可搬。

## 6. TOC 与 prev/next

- **TOC 数据全部编译期抽取**（除 VitePress 运行时扫 DOM——它没有编译期 content 层，我们有自己的 `headings`，明确避开此路）。h1 一律不进 TOC（Nextra/Docusaurus 显式，h1 是页标题）。Docusaurus 讲究「先树化后过滤」：`h3-h2-h4` 不会误挂父子关系。层级过滤三家都有全局配置 + 页面级 frontmatter 覆盖。
- **prev/next 全部由 sidebar 平铺序派生**（VitePress/Starlight/Nextra），只有 Docusaurus 加了页面级覆盖（`pagination_next/prev`，可 null 关闭）。隐藏项/外链项不在序列里。无一家做独立的手配 prev/next。

## 7. CSS 体系

- **令牌规模差异大**：VitePress 292 个 `--vp-*`（含完整 hue 色阶 -1/-2/-3/-soft）vs Docusaurus theme-classic 实际引用 43 个 `--ifm-*`。令牌越多可定制面越广，但公共承诺面也越大。
- **暗色 = 同 token 重声明**（四家一致）：`[data-theme=dark]`/`.dark` 下重定义同名变量，组件零改动。
- **内容 scope**：VitePress `.vp-doc`、Docusaurus CSS modules、Nextra `x:` 前缀——正文样式必须 scope，否则污染用户自定义页。**Marko `<style>` 块是提取且全局的**，正文元素选择器必须包 scope 类。
- **加载顺序**：Docusaurus customCss 明确追加在 Infima 之后（覆盖靠后者胜）；Starlight 用 cascade layers 让用户 CSS 自然胜出。同特异性顺序决定覆盖——与我们暗色规则踩坑（dark 覆盖必须在后）同根。

## 8. 性能相关的注意点

- **Nextra 全量 pageMap 进客户端 + 每导航 O(n) normalize**：被 Next.js 客户端路由逼的。markopress 是 SSG：gen-routes 阶段可预计算每路由所需切片，全树只留给搜索场景。**「文件树全自动」与「性能」可以解耦**。
- **SSG 每页内嵌整树**：VitePress/Starlight 的静态 HTML 每页都带完整 sidebar 渲染。5000 页夹具下这是每页 HTML 写放大——sidebar 按「集合 → 是否进侧边栏」映射控制规模（perf 形态只挂 docs 集合）。
- **dev 期禁用重查询**：Nextra dev 不查 git 时间戳（仅 prod），5000 页每页一次 git 查询会拖垮增量。凡 per-entry 的外部进程查询（git/网络）都应有 dev 开关或预算。
- **Docusaurus docs 版本路由全挂同一 Layout 下**：跨版本导航不重挂布局、sidebar 状态保留——marko-run 布局是构建期融合单入口，天然同构，无此问题。

## 9. 对 markopress 的设计启示（喂给设计方案）

1. **采纳 Docusaurus 的字符串槽位契约**：生成器只写死槽位 tag 名（`mp-layout`/`mp-page`），主题包用 `marko.json` tags-dir 提供实现（文件名=tag 名，mp-spike-search 已验证）。数据面（gen-routes）与实现面（主题包）完全解耦，Marko 组件编译期单文件，比 React 组件树更适合整件替换。
2. **采纳 Nextra ①**：主题输入契约 = 显式的 normalize 产物（sidebar 树/平铺序/per-page 邻居），而非散装 nav.json。纯函数放共享层（双路纪律），gen 时算树给布局，渲染路径算 per-page 切片（digest 缓存）。
3. **排序链取共识骨架**（§3.2）：frontmatter `order` > 数字前缀 > index 置顶 > localeCompare。目录级 meta 文件（`_meta`/`_category_` 等价物）推迟——v1 先验证骨架。
4. **定制面 v1 挡在第 1–3 层**（CSS 变量 + 配置），不做组件覆写/swizzle（第 4–5 层推迟）。若将来做：wrap 优先、原件可寻回、每槽位配类型契约与稳定性分级、未声明默认档有立场。
5. **暗色照 §5 共识**：`data-theme` 属性 + pre-paint 内联脚本 + namespaced localStorage 键 + 三态（亮/暗/系统）。主题状态不进 Marko state（resume 安全）。shiki 双主题从 `prefers-color-scheme` media 查询改为 `[data-theme="dark"]` 选择器。
6. **TOC 用现有编译期 `headings`**（h2 起，先树化后过滤语义），prev/next 由 sidebar 平铺序派生（页面级覆盖推迟）。
7. **CSS**：`--mp-*` 令牌（v1 控制在小规模，学 Docusaurus 43 个而非 VitePress 292 个），暗色同 token 重声明，正文 scope `.mp-doc`，`<style>` 走 markopack style channel（已落地）。
8. **主题包结构**（D5 定稿的落点）：`@markopress/theme-docs` = tags（mp-layout/mp-page）+ marko.json + 令牌 CSS；框架层（框架/内容/生成器）不依赖主题，主题也不反依赖框架（比 Nextra 的 peer 强耦合干净）。
